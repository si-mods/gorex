# DSK-015: Omarchy desktop integration

Status: phase 1 built (#1188): the automatic following, `status`, and `bind`/`unbind`. Phase 2 (a Settings switch) not built.

This doc decides how GoRex follows an Omarchy desktop. It builds on the
theme framework of [DSK-008](DSK-008-theme.md). GoRex ships the reader,
never a look (DSK-008, Non-goals).

## Problem

Omarchy is an Arch-based desktop with its own theme system. The active
theme is in `~/.local/state/omarchy/current/theme/`: its `colors.toml`,
its name in `~/.local/state/omarchy/current/theme.name`, and one rendered
file per template.

GoRex installs a `.desktop` file, so the app launcher lists it. Nothing
else joins the two programs. When the desktop changes colors, GoRex keeps
its built-in palette.

Omarchy signals a hard-coded list of applications on a theme change. A
third-party application cannot add itself to that list. The only trigger
that Omarchy offers to user scripts is `~/.config/omarchy/hooks/theme-set.d/`,
and a hook runs after Omarchy's own scripts, about a second later.

## Goal

- GoRex follows the active Omarchy theme with no command by the user.
- A theme change repaints the open window at the moment Omarchy swaps
  the theme, not a second later.
- GoRex writes nothing into the desktop's configuration.
- An explicit `appearance.theme` keeps the user's choice.
- `appearance.omarchy: false` turns the following off.
- One optional command adds a key binding that starts GoRex.

## Non-goals

- No hook file in `~/.config/omarchy/hooks/theme-set.d/`. It runs late,
  and it writes into another application's configuration.
- No write into `~/.config/omarchy` or `~/.config/hypr`, except the
  optional binding command.
- No terminal colors. `terminal.theme` stays the user's choice
  ([DSK-009](DSK-009-terminal-settings.md)).
- No built-in Omarchy palette. The manifest is made from the desktop's
  data (DSK-008, Non-goals).
- No macOS or Windows support. The reader finds nothing there and leaves
  the built-in palette.

## Design

### Behavior

At startup, and when the settings change, GoRex does this:

1. It finds the Omarchy root: `$OMARCHY_PATH`, else `/usr/share/omarchy`.
   It requires `version` and `bin/omarchy-theme-current`.
2. It reads the palette and the theme name. A missing file means that
   GoRex keeps the built-in palette, with one warning in the log.
3. It applies the palette in this order:

   1. `appearance.theme` names a theme pack: that pack wins.
   2. Omarchy is found and `appearance.omarchy` is not false: the
      desktop's palette wins.
   3. Else the built-in palettes win.

4. It watches `~/.local/state/omarchy/current/` while the window is open.
   Omarchy renders the next theme in a sibling directory and renames it
   into place, so the watch sits on the parent that survives the swap.

A theme change re-reads the palette, compares it with the palette in use,
and repaints the window when the palette changed. Nothing else happens.

`gorex omarchy status` prints the detection, the theme name, the mode,
whether the window follows the desktop, and the keys of the binding.
With `--json` it prints one object.

`gorex omarchy bind [--keys KEYS]` adds a block to
`~/.config/hypr/bindings.lua`, with `SUPER + SHIFT + R` by default.
`gorex omarchy unbind` removes the block. Neither runs without Omarchy.

### Model

The palette resolves like `omarchy-theme-color --all`, the script that
every Omarchy consumer uses. The table gives the six keys that the
manifest takes, and each fallback in order:

| Key | Fallbacks |
| --- | --- |
| `background` | `bg`, `color0` |
| `darker_background` | `darker_bg`, otherwise `background` mixed 50% toward black |
| `lighter_background` | `lighter_bg`, `color0`, `background` |
| `foreground` | `fg`, `color7` |
| `muted` | `color8`, `dark_foreground`, `foreground` |
| `accent` | `blue`, `color4`, `foreground` |
| `selection` | `selection_background`, `color8`, `color0`, `background` |
| `red` | `color1`, `accent` |
| `green` | `color2`, `accent` |
| `yellow` | `color3`, `accent` |

The mode is `mode`, else `theme_type`, else `light` when a `light.mode`
file sits beside `colors.toml`, else the sum of the background's red,
green and blue bytes above 382 means `light`, else `dark`.

A value that is not a hex color is dropped, and the next fallback is
tried. A key with no fallback is left out of the manifest, and the
built-in seed stands (DSK-008).

The manifest is the shape of a theme pack, made in memory and never
written: name `Omarchy`, description `Omarchy theme <name> (generated by
gorex)`, the seeds of the current appearance only, and the role
`sideBar.tabActiveBackground` set to `selection`.

| Seed | Key |
| --- | --- |
| `bgTop` | `background` |
| `panel` | `lighter_background` |
| `text` | `foreground` |
| `textMuted`, `textFaint`, `iconMuted` | `muted` |
| `accent` | `accent` |
| `danger` | `red` |
| `done` | `green` |
| `attention` | `yellow` |

The manifest also sets the faces that the seeds do not reach, so that the
chrome matches the desktop and not only its accents:

| Role | Key |
| --- | --- |
| `sideBar.background` | `background` |
| `titleBar.background` | `darker_background` |
| `paneHeader.background`, `button.background`, `dropdown.background`, `windowControl.background` | `lighter_background` |
| `sideBar.tabActiveBackground` | `selection` |
| `sideBar.tabHoverBackground`, `sideBar.trackBackground` | `lighter_background` |
| `sideBar.tabSeparator` | `darker_background` |
| `pane.border` | `selection` |

The binding block sits between `-- gorex omarchy: begin` and
`-- gorex omarchy: end`, so a write replaces it and `unbind` removes it.
Every other line of the file stays.

### Code

- `internal/omarchy`: `Detect`, `ReadPalette`, `Manifest`, `Bind`,
  `Unbind`, `Status`. Paths arrive as fields, so tests use temp
  directories.
- `omarchywatch.go` in the root package: applies the palette at startup
  and after a settings change, and watches the theme directory with
  `mygo.WatchFiles`. A change posts to the main thread, compares the
  palette, and calls `applyTheme`.
- `settings.go`: the `appearance.omarchy` key, a pointer to a bool, so
  that an absent key means true.
- `internal/cli/omarchy.go`: `status`, `bind` and `unbind`.

## Alternatives

- **A hook in `theme-set.d`**: rejected. It needs an install step, it
  runs about a second after the swap, and it writes into the desktop's
  configuration.
- **A script named `omarchy-theme-set-gorex`**: rejected. Omarchy runs a
  fixed list of these scripts from its own directory. A third-party
  application cannot add itself.
- **A template in `~/.config/omarchy/themed/`**: rejected. It renders
  into the theme directory, so the application must copy it from there,
  and the user must put the template in place.
- **Polling the file**: rejected. The swap is observable, and a poll
  wastes power.
- **A theme pack that the user installs**: rejected. It is a look that
  does not follow the desktop after the next theme change.

## Security

GoRex reads two files of the user's desktop and writes nothing there.
With `gorex omarchy bind` it writes one block into Hyprland's binding
file, and refuses a symlink. The manifest holds hex colors and a name
only, within the parse limits of `internal/theme`.

## Migration

Nothing changes for a user without Omarchy. An explicit
`appearance.theme` wins, so a user who picked a theme pack keeps it.
`appearance.omarchy` is new, and an absent key means true.

## Tests

- Palette: a table of `colors.toml` inputs and manifest seeds, with a
  legacy ANSI-only palette and a palette with no accent.
- Mode: `mode`, `theme_type`, a `light.mode` file, and the luminance
  rule.
- Precedence: an explicit `appearance.theme` wins, `appearance.omarchy:
  false` disables, and a machine without Omarchy keeps the built-ins.
- Watch: a rename of a sibling theme directory applies the new palette
  once, and an event with the same content applies nothing.
- Binding: insert, replace and remove keep the user's other lines, and a
  symlink is refused.
- CLI: exit codes and `--json` shapes against a fake Omarchy root and a
  temp home.
